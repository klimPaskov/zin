## Why the faces are redefined, not only the global table

Every light-on-dark face the design system's roles use (`hoi_16mbs`, `hoi_18mbs`, `hoi_20bs`, `hoi_20b`, `hoi_24header`, `hoi_30header`, `hoi_36header`) and the common vanilla faces (`hoi_18`, `hoi_18b`, `hoi_30`, `vic_18`, `vic_22`, `vic_36`, `Arial12`, `nsb_hoi_24header`, `nsb_hoi_36header`) carry their own `textcolors` block in the installed `interface/core.gfx` (lines 794 to about 1400) listing `G`, `R`, `Y`, `H`, `T` (and `O`, `g` for `hoi_16mbs`). The wiki ("Font modding", section "Defining bitmaps": "`textcolors` provides an override of text colours ... when used on this font") and the Localisation page ("It is also possible to make a colouring character represent a different colour from default when a certain font is used") say that a face's own block wins for that face. A global table alone would therefore change only Garamond, `cg_16b` and the faces without a block, and `§G` would keep two meanings. Faces drawn dark on light grounds (`vic_18_black`, `vic_36_black`) and the map and decorative faces (`tahoma_60`, `hoi_22tech`, `hoi_33`, `hoi_arrow_font`, `null_font`) are not redefined.

## Evidence that the engine accepts an additive block

| Source | What it shows |
| --- | --- |
| Installed game, `interface/core.gfx:794`, `interface/fonts.gfx:2`, `interface/chatfonts.gfx:2`, `interface/load_screen_font.gfx:1`, `interface/core_chinese.gfx:1` | Five vanilla files each open their own top-level `bitmapfonts = { ... }` block; the engine reads every `interface/*.gfx` and merges them. An additional file with its own block is the vanilla pattern. |
| Wiki snapshot `paradox_wiki/Font modding - Hearts of Iron 4 Wiki.md`, lines 132 to 158 | "an entry must be created in a `/Hearts of Iron IV/interface/*.gfx` file" (any file); the `textcolors` override per font. |
| Wiki snapshot `paradox_wiki/Localisation - Hearts of Iron 4 Wiki.md`, line 164 | Text colours are the `textcolors` array; a face may redefine a code. |
| Approved reference mod 2265420196 (Old World Blues), `interface/zzz_fonts.gfx` lines 1 to 40 | A mod that ships no `core.gfx` defines its whole global `textcolors` table in an additive `zzz_` file. |
| Same mod, `interface/z_fallout_font.gfx` lines 203 to 270 | Redefines the vanilla faces `hoi4_typewriter16_inverted` and `hoi4_typewriter22` with other glyph files in an additive file; the precedent for both the per-face colours and the typewriter alias. |
| Installed documentation folder (`documentation/*.md`) | No font or text-colour section (searched for `bitmapfont`, `textcolors`, `fonts`): a coverage gap, recorded. |
| MCP renderer (`hoi4.gui_render` 4.6.1, `gui/source-graph.js` and `gui/assets.js`) | Reads every `bitmapfonts` block and lets the mod's face definition win; the renders below show `§Y` drawn `#f5ead1` in `hoi_18mbs` (layout JSON of `z_realm_1920`, colour runs). This is the offline model, not the engine. |

The OWB precedent shows that a mod relies on a later same-name `bitmapfont` replacing the vanilla one; the order of `interface/*.gfx` reading (alphabetical, `zz_` after `core.gfx`) is the assumption the Linux run must confirm.

## What only the Linux run can confirm

1. That the engine reads `interface/zz_zin_textcolors.gfx` after `core.gfx` and the later `bitmapfont` of the same name replaces the earlier one (no "duplicate font" line in `error.log`); otherwise drop the redefinitions from `textcolors.json` and keep the global block (the asset baseline entries then disappear as fixed).
2. That a second global `textcolors` block is merged or replaces the first (it is written whole, so either works) and `§G`, `§R`, `§Y` show the token colours in a tooltip (`cg_16b`), an event body (Garamond), a decision row (`hoi_16mbs`) and a ZIN panel (`hoi_18mbs`).
3. That the windows using the typewriter faces (25 vanilla `.gui` files, among them `eventwindow.gui`, `countrydecisionview.gui`, `countryintelligenceagencyview.gui`, `operationoverview.gui`, `unitleaderwindow.gui` and the designers) draw Garamond without clipped lines from the different metrics (`garamond_24.fnt` has line height 24 against 22 for `hoi4_typewriter22.fnt`, the same baseline 18).
4. That the `bitmapfont_override` blocks of `core.gfx` for Russian, Polish and Japanese still apply to the redefined names (ZIN ships only English text; the other languages fall back to the vanilla glyphs, which is accepted).

## Simplifications, omissions and blockers

- Resolved by the lead (31 October 2026): `§Y` and `§H` keep a distinct gold (`text.highlight`); the renders and metrics above were taken with the earlier `text.title` mapping. The gold is darker than `text.title` and its measured ratios are above every threshold, so no check 19 finding can appear from it; a rerender was not run after the change (the verify below covers the build).
- The dark faces drawn on paper (`hoi4_typewriter16`, `hoi4_typewriter22`, `vic_18_black`, `vic_36_black`) keep their installed per-face colours: the design system has no ink-ground tokens for `G`, `R`, `Y`.
- No other simplification.
