# Contract additions register

**Status:** Ready. Reviewed 19 October 2026 against CONVENTIONS "Status"; integrated 19 October 2026. **Priority:** 3. **Phase:** 3. Regenerated on 19 October 2026 from every spec after the Ready reviews; the integration round of the same day applied the reviewers' requests and decisions E7, F4, F7, N12–N16, O3–O7 and R1.

## Purpose

[00_shared_contract.md](00_shared_contract.md) lists the story flags, variables, characters and naming rules every system shares. This register lists every other name that one spec defines and another spec uses. It applies decision N11 of [INTEGRATION_DECISIONS.md](../INTEGRATION_DECISIONS.md): each name has **one owning spec**, which defines it; every other spec uses it with that meaning.

## Rules

1. **One name, one meaning, one owner.** The "Owner" column names the spec that defines the name. A spec that needs a name defined elsewhere uses it as written here and never declares a second name for the same thing.
2. **Kinds may share a name only inside one owner.** The engine keeps flags, variables, ideas, decision categories and characters apart, so an owner may use one name for, say, a flag and the idea it gives. The row lists every kind. Two owners never share a name.
3. **Retired names** (below) must not appear in any generated file. The build's name check fails on them. A name in quotes is game text and is checked in localisation; a name followed by a kind in parentheses is retired for that kind only, and its other kinds stay listed.
4. **Scope.** A name is listed when a spec other than its owner (or the owner's own focus tree) uses it, when files of two builder modules carry it, or when a reviewer asked for it to be held for one owner ("Also used by" then says —). Names used only inside one mechanic and its tree stay in that mechanic spec. Contract names are not repeated here.
5. **Patterns** (below) cover families of names that follow one rule, for example `zin_people_<key>`. Their members need not be listed; a member listed in the names table gives its owner and meaning, and that row wins over the pattern's owner.
6. **Changes.** A spec that needs a new shared name, or a change of meaning or owner, sends a request through the integrator. Requests wait in "Pending requests" at the end until the integrator applies them here and in the owning spec.
7. **Build check.** The content builder's name check reads this table: a generated `zin_` name that is shared but not listed, or listed under two owners, fails the build.

## Implementation

- This file is design data. A new build check, `tools/content/checks/names.mjs`, parses the three tables (retired names, patterns, names) and runs over the staged tree in `tools/content/build.test.mjs`.
- Retired names match whole names only: `zin_rule_golden_king` does not match `zin_rule_golden_king_death`. Event ids match exactly (`zin_glo.10`, not `zin_glo.100`). A `<key>` placeholder matches `[a-z0-9_]+`. A quoted retired text is checked in `localisation/` only. A kind-qualified row is checked only where that kind is defined or used: a character in `common/characters` and in character references (`zin_zol` (character) never matches the Zol tree's event namespace `zin_zol` or `zin_zol_will`), an idea in `common/ideas` and idea effects, an opinion modifier in `common/opinion_modifiers` and `add_opinion_modifier`.
- The check fails when a retired name appears in a staged file; when a staged `zin_` name is used in files written by two builder modules and is neither in the contract, nor in the names table, nor matched by a pattern; or when one name is listed twice.
- The register is regenerated by the integrator when specs change; the scope rule (rule 4) decides which names it lists.

## Acceptance

1. Every name appears in the names table at most once, with exactly one owner, and no retired name is in the names table except the other kinds of a kind-qualified retirement.
2. Every owner link resolves to an existing spec, and the owner spec mentions the name (patterns and event-id rows excepted).
3. `npm test` in `tools/` runs the name check; a planted retired name in a staged file makes it fail, while `zin_zol_will`, the event `zin_zol.1` and `zin_glo.100` do not (negative tests).
4. Every name that decisions N1–N16, O3–O7, R1, E7, F4 and F7 retire is in the retired table, and every name they keep is in the names table or the contract.
